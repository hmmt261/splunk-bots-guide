[[chap_botsv3_aws]]
== BOTSv3 (1): AWS 環境とコインマイニング

=== シナリオ

BOTSv3 も舞台は Frothly である．2018 年 8 月 20 日，Frothly のクラウド環境と社内端末で複数の問題が起きた．

* IT 担当の Bud Stoll（`bstoll`）が，誤って S3 バケットを一般公開してしまう
* GitHub に AWS のアクセスキーが流出し，第三者がそのキーで AWS を操作しようとする
* 社内端末のブラウザで，Web サイトに埋め込まれたコインマイナー（Coinhive）が動く

この章では問題 2100〜2119 を扱う．
主に使うデータは次のとおり．

* `aws:cloudtrail`：AWS API の呼び出し記録
* `aws:s3:accesslogs`：S3 バケットへのアクセス記録
* `hardware` / `winhostmon`：サーバー・端末の構成情報
* `PerfmonMk:Process`：Windows のプロセスごとの CPU 使用率
* `symantec:ep:*`：Symantec Endpoint Protection
* `stream:smtp` / `stream:dns`：メールと DNS

.CloudTrail のよく使うフィールド
[cols="2,3", options="header"]
|===
|フィールド |内容

|`eventName` / `eventSource`
|呼び出された API と，そのサービス（`s3.amazonaws.com`，`iam.amazonaws.com` など）

|`userIdentity.userName` / `userIdentity.accessKeyId` / `userIdentity.type`
|呼び出した IAM ユーザー，使われたアクセスキー，主体の種類

|`requestParameters.*` / `responseElements.*`
|API の引数と応答

|`errorCode` / `errorMessage`
|失敗したときのエラー

|`userAgent`
|呼び出したクライアント（AWS CLI，SDK，コンソールなど）

|`eventID`
|イベントを一意に識別する ID
|===

[[q2100]]
=== 2100: AWS にアクセスした IAM ユーザー

[quote]
____
List the IAM users that accessed an AWS service (successfully or unsuccessfully) in Frothly's AWS environment. Comma separated without spaces, in alphabetical order.
____

配点：20 点

.方針
CloudTrail で，主体の種類が IAM ユーザー（`userIdentity.type=IAMUser`）のイベントを，ユーザー名ごとに数える．

[source,spl]
----
index=botsv3 sourcetype=aws:cloudtrail userIdentity.type=IAMUser
| stats count by userIdentity.userName
----

`bstoll`，`btun`，`splunk_access`，`web_admin` の 4 ユーザーである．
成功・失敗を問わないので，`errorCode` では絞らない．

.答え
[%collapsible.answer]
====
`bstoll,btun,splunk_access,web_admin`
====

=== 2101: MFA なしの API 操作を検知するフィールド

[quote]
____
What field would you use to alert that AWS API activity has occurred without MFA?
____

配点：10 点

.方針
CloudTrail のイベントには，そのセッションが MFA（多要素認証）で認証されたかを示す属性がある．

[source,spl]
----
index=botsv3 sourcetype=aws:cloudtrail
| stats count by userIdentity.sessionContext.attributes.mfaAuthenticated
----

`userIdentity.sessionContext.attributes.mfaAuthenticated` の値が `false` のイベントが，MFA なしの API 操作である．
問題はフィールド名を問うているので，ドット区切りの完全なパスを答える．

WARNING: コンソールへのログイン（`ConsoleLogin`）には `additionalEventData.MFAUsed` というフィールドもあるが，
これはログイン時だけのもので，API 操作全般には使えない．

.答え
[%collapsible.answer]
====
`userIdentity.sessionContext.attributes.mfaAuthenticated`
====

=== 2102: Web サーバーのプロセッサ番号

[quote]
____
What is the processor number used on the web servers?
____

配点：10 点

.方針
Web サーバーを特定してから，構成情報（`hardware`）の CPU の型番を読む．

[source,spl]
----
index=botsv3 sourcetype=access_combined
| stats count by host
----

Web サーバーのアクセスログ（`access_combined`）を出しているのは，`gacrux.*` という名前のホスト群と `hoth` である．
このうち構成情報（`hardware`）があるのは `gacrux.*` だけなので，そちらを調べる．

[source,spl]
----
index=botsv3 sourcetype=hardware host=gacrux*
| table host _raw
----

----
CPU_TYPE              Intel(R) Xeon(R) CPU E5-2676 v3 @ 2.40GHz
----

Intel のプロセッサ番号は「`E5-2676`」の部分である（`v3` は世代を表す）．

.答え
[%collapsible.answer]
====
`E5-2676`
====

[[q2104]]
=== 2104: S3 バケットを公開した API の `eventID`

[quote]
____
Bud accidentally makes an S3 bucket publicly accessible. What is the event ID of the API call that enabled public access?
____

配点：10 点

.方針
S3 バケットのアクセス権（ACL）を変える API は `PutBucketAcl` である．
ACL の付与先（Grantee）に「全員（`AllUsers`）」が含まれるものを探す．

[source,spl]
----
index=botsv3 sourcetype=aws:cloudtrail eventName=PutBucketAcl
| spath path=requestParameters.AccessControlPolicy.AccessControlList.Grant{}.Grantee.URI output=grantee
| sort _time
| table _time eventID userIdentity.userName requestParameters.bucketName grantee
----

[cols="1,3,1,1,3", options="header"]
|===
|`_time` |`eventID` |`userIdentity.userName` |`requestParameters.bucketName` |`grantee`
|13:01:46 |`ab45689d-69cd-41e7-8705-5350402cf7ac` |`bstoll` |`frothlywebcode` |`.../s3/LogDelivery` `.../global/AllUsers`
|13:57:54 |`9a33d8df-1e16-4d58-b36d-8e80ce68f8a3` |`bstoll` |`frothlywebcode` |`.../s3/LogDelivery`
|===

`grantee` の値は `+http://acs.amazonaws.com/groups/global/AllUsers+` のような URI で，表では先頭を省略している．

13:01:46 の呼び出しで `AllUsers` に `READ` と `WRITE` が付与され，13:57:54 の呼び出しで元に戻されている．
公開したのは 1 件目である．

.答え
[%collapsible.answer]
====
`ab45689d-69cd-41e7-8705-5350402cf7ac`
====

=== 2107: 公開中にアップロードされたテキストファイル

[quote]
____
What is the name of the text file that was successfully uploaded into the S3 bucket while it was publicly accessible?
____

配点：10 点

.方針
S3 のアクセスログで，公開されていた時間帯（13:01:46〜13:57:54）のオブジェクトのアップロード（`REST.PUT.OBJECT`）を探す．

[source,spl]
----
index=botsv3 sourcetype=aws:s3:accesslogs frothlywebcode REST.PUT.OBJECT *.txt
| table _raw
----

結果の `_raw` に記録された時刻が，公開されていた時間帯に入っているかを確かめる．

----
... frothlywebcode [20/Aug/2018:13:02:44 +0000] 52.66.146.128 - ... REST.PUT.OBJECT OPEN_BUCKET_PLEASE_FIX.txt "PUT /OPEN_BUCKET_PLEASE_FIX.txt HTTP/1.1" 200 ...
----

公開の約 1 分後に，外部のアドレスから `OPEN_BUCKET_PLEASE_FIX.txt`（「バケットが公開されているので直してください」）が置かれ，
ステータス 200 で成功している．公開バケットを探して回る第三者による書き込みである．

NOTE: 同じ時間帯には `frothly_html_memcached.tar.gz` など `.txt` 以外のファイルもアップロードされている．
問題はテキストファイルを問うているので `*.txt` で絞る．

.答え
[%collapsible.answer]
====
`OPEN_BUCKET_PLEASE_FIX.txt`
====

[[q2109]]
=== 2109: コインマイニングで最初に CPU 100% に達したプロセス

[quote]
____
A Frothly endpoint exhibits signs of coin mining activity. What is the name of the first process to reach 100 percent CPU utilization from this activity on this endpoint?
____

配点：15 点

.方針
2110 で分かるとおり，マイニングをしていた端末は `BSTOLL-L` である．
この端末のプロセスごとの CPU 使用率（`PerfmonMk:Process` の `%_Processor_Time`）が 100% に達したプロセスを，最初に 100% に達した時刻の順に並べる．

[source,spl]
----
index=botsv3 host=BSTOLL-L sourcetype=PerfmonMk:Process instance!=Idle instance!=_Total
| where '%_Processor_Time'>=100
| stats min(_time) as first count by instance
| sort first
| eval first=strftime(first, "%F %T")
----

[cols="2,2,1", options="header"]
|===
|`instance` |`first` |`count`
|`MicrosoftEdgeCP#2` |2018-08-20 09:36:26 |1
|`chrome#5` |2018-08-20 13:37:50 |3
|`chrome#4` |2018-08-20 13:38:30 |129
|`MsMpEng` |2018-08-20 14:04:31 |1
|===

2110 で見る Coinhive への DNS 問い合わせは 13:27〜13:39 に集中しており，この時間帯の中で CPU 使用率が上昇している（13:37〜）．
9:36 の `MicrosoftEdgeCP#2` は 1 回だけの一時的な負荷で，マイニングとは関係がない．
マイニングによって最初に 100% に達したのは `chrome#5` である．

NOTE: `instance` は Perfmon のインスタンス名で，同じ名前のプロセスが複数あると `#番号` が付く．
問題は実行ファイル名（`chrome.exe`）ではなくインスタンス名を期待している．

WARNING: 「from this activity（このマイニング活動による）」を読み落として `MicrosoftEdgeCP#2` を答えると不正解になる．
writeup では `MicrosoftEdgeCP` 系の候補を 3 つ試して外したチームがあった．

.答え
[%collapsible.answer]
====
`chrome#5`
====

| stats count by host
----

.答え
[%collapsible.answer]

[[q2111]]
=== 2111: コインマイナーの最初のシグネチャ ID

[quote]
____
Using Splunk's event order functions, what is the first seen signature ID of the coin miner threat according to Frothly's Symantec Endpoint Protection data?
____

配点：15 点

.方針
Symantec のログからコインマイナーの検知を取り出し，「イベントの順序」を扱う関数（`first`/`last`）でシグネチャ ID を調べる．

[source,spl]
----
index=botsv3 sourcetype=symantec:ep:security:file JSCoinminer
| rex "CIDS Signature ID: (?<sid>\d+)"
| stats first(sid) as first last(sid) as last earliest(sid) as earliest latest(sid) as latest
----

[cols="1,1,1,1", options="header"]
|===
|`first` |`last` |`earliest` |`latest`
|30356 |30358 |30356 |30358
|===

検知されたシグネチャは `30356`（`JSCoinminer Download 6`）と `30358`（`JSCoinminer Download 8`）の 2 種類で，
多くのイベントで両者が同じ時刻に記録されている．

Splunk の検索結果は新しい順に並ぶので，「最初に見られた（first seen）」イベントは結果の **最後** にある．
結果の最後の値を返す `last(sid)` が `30358` である．
実際に結果を古い順に並べ直すと，最も古い時刻（13:37:40）には `30358` と `30356` の 2 件があり，先頭に来るのは `30358` である．

[source,spl]
----
index=botsv3 sourcetype=symantec:ep:security:file JSCoinminer
| rex "CIDS Signature ID: (?<sid>\d+)"
| reverse
| head 3
| table _time sid
----

WARNING: `earliest(sid)` は時刻が同じイベントの中からどちらを選ぶかが決まっておらず，この問題では `30356` を返す．
`30356` を提出すると不正解になる（<<sec_pitfalls>>）．

.答え
[%collapsible.answer]
====
`30358`
====
